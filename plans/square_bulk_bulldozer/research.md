# Bulk Bulldozer (`square_bulk_bulldozer`): research notes

Status: done 2026-10-07 (research for rev 1). Still the evidence base: the mod code cites it as "research §N".

Evidence for `PLAN.md`. Paths are relative to the repo root; `.cache` is gitignored (search with `rg -uu`). "Verified" means a base-game or shipped-mod source does exactly this; "inferred" means the API declares it but no source in the repo uses it that way; "unknown" means it needs an in-game test (listed in PLAN.md "Open questions").

## 1. How a mod adds a tool with an options bar

**Mechanism: a `construction_tool` resource with a custom action.** No ToolStack push is needed: the construction menu mounts the tool for us.

- `content/<dir>/<name>.res.lua` returns `{ type = "construction_tool", data = { getDefinitionFn = { fileName = resolve("<name>.script@getDefinition") } } }`.
  - Base: `.cache/game/base/content/gui/construction/tools/vegetation_eraser_tool.res.lua:1-10`, `player_owned_tool.res.lua`, `marketing_campaign_tool.res.lua`.
  - Mod (verified it loads from a mod, mod.json has no script hooks at all): `.cache/subscribed/move_it_probe_overpass/content/tools/overpass_probe/overpass_probe.res.lua:1-10`, `mod.json` (`severityAdd`/`severityRemove` both `None`), `content/mod.script.tl` (empty `data()`).
- `getDefinition(resName, repository, params) : ConstructionDefinition` (type: `.cache/game/base/tealdef/gui/construction/construction_menu.d.tl:202-245`). Fields we use: `resName`, `name`, `description`, `icon`/`previewIcon` (`{icon = resolve("x.tga")}`), `availability = {yearFrom=0, yearTo=0}`, `action = "ACTION_CUSTOM"`, `customAction = {recipe, customParam}`, `params = {ConstructionMenuParam}`, `menuCategory = {categories = {{category=..., order=...}}}`, `constructions = {}`, `categories = {}`, optional `hudIcons`, `builderAudioRes`.
  - Base custom-action tool: `marketing_campaign_tool.script.tl:23-140` (`ACTION_MARKETING` + `customAction`). Mod: `overpass_probe.script.tl:5569-5583` (`ACTION_CUSTOM`, `makeCustomAction` cast helper at 5569-5571).
- **The recipe contract** (`ConstructionCustomActionParams<P>`, `construction_menu.d.tl:168-176`): `gameCtx`, `definition`, `customParam`, `isActive`, `abort()`, `setActionFn(fn, key2)`, `getCurrentParams()`.
  - The menu mounts `customAction.recipe{...}` while the entry is selected and calls `abort()` on every step once the entry is no longer the active list index or the tab is hidden (`.cache/game/base/content/gui/construction/construction.tl:401-436`).
  - Canonical body: `construction_react_util.RegisterCustomSelectorBasedActionRecipe` (`.cache/game/base/content/gui/construction/construction_react_util.tl:1282-1442`). It returns nothing (no layout), and when `params.isActive` calls `params.setActionFn(actionFn, recipeName..tostring(definition))`. `actionFn` runs inside the world-tool layer and returns `builtin.ActionDescriptor{ tool, onBack = params.abort, children = {Selector, HudIconManagerConfig, ActionTooltip, LayerConfig}, crosshair, terrainCirclePolicy, mouseCursor }` (1395-1421).
  - ESC/back: in mouse mode the base lets IA_MENU_BACK fall through "so it will close the construction window"; only in gamepad mode does it bind IA_MENU_BACK to `abort` (1437-1441). `ActionDescriptor.onBack = abort` (1416).
- **Menu entry position.** `overpass_probe.script.tl:6181-6217` explains that `order` must stay below the first year-gated entry of the category (they use `roads_tools`, order 20) because `isActionActive(listIndex)` compares the selected definition index with the entry's position (`construction.tl:758-760`, used by the abort check at 427). Mouse mode survives a mismatch but gamepad mode breaks. Use a low order (5).
  - Categories (`.cache/game/base/content/gui/construction/menu/menu_categories/`): `roads_tools` (menu ROADS), `road_tools` (ROAD), `rail_tools` (TRACKS), `landscaping_terrain` (LANDSCAPING). The bulldozer itself is a single, sub-tab-less category built in code (`construction.tl:4050-4080`, `addSingleCategory`), so a mod cannot add a tab under it.
  - Pitfall: a category whose only definition has `resName` containing "eraser" is hidden (`construction.tl:4021`). Don't name files `*eraser*`.
- **Options bar = `params` with `location = ScriptParamLocation.Toolbar`.**
  - Types: `Button`, `Slider`, `ComboBox`, `IconButton`, `CheckBox` (`.cache/game/api/tealdef/api/type.d.tl:1961-1967`).
  - Slider with `values` (labels) + `numbers`: `onChangeFn(newValue)` receives the number, `defaultIndex` is 1-based (`overpass_probe.script.tl` `overpass_height`, ~5739-5765: `defaultIndex = 9` = 8 m).
  - CheckBox: `values = {Off, On}`, no `numbers`, `onChangeFn` gets a 1-based index, 2 = checked (`overpass_probe.script.tl` `overpass_live_preview`, comment "CheckBox callbacks receive a one-based value index: 2 means checked").
  - `onChangeFn` does not fire at tool mount (`overpass_probe.script.tl:227-237`).
  - The bar can't show dynamic text (names/tooltips are baked at definition time, `overpass_probe.script.tl:246-250`). Live numbers go in an `ActionTooltip` near the cursor instead.
  - Getting values into the recipe: `params.getCurrentParams()` (`construction.tl:419-422`, returns `{key: number}`; whether it holds the index or the `numbers` value is **unknown**). The proven bridge is `onChangeFn` → `api.gui.fireReactEvent(name, payload)` → `react.onEvent(name, fn)` in the recipe (`overpass_probe.script.tl:5255-5295`).
- Base brush slider helper: `construction_react_util.getBrushConstructionParams` (`construction_react_util.tl:2891-2990`): a "Brush Size" slider from `makeSizes(numSizes, min, max, scale)`. The base asset brush max is 256 (`.cache/game/base/content/base/mod.script.tl:90`).
- Input prompt hints for a custom tool: CSS `!input-controller R::<Recipe>` / `!input-mouse R::<Recipe>` with `actionPromptList` (`overpass_probe.css.lua:1-30`). Optional.

## 2. Selector, mouse events and the cursor

- `builtin.Selector` params (`.cache/game/base/content/scripts/builtin.d.tl:1392-1415`): `onSelect`, `onSelectSecondary`, `onHover`, `filter`, `stopOnMenuBack`, `onProcessMouseEvent(evt) : boolean`, `selectionColor`/`selectionOutlineColor`/`selectionOutlineColor1`, `circleBorderColor`/`circleFillColor`/`circleBorderWidth`/`circleAnimEasing`/`circleAnimDuration`, `crosshairColor`.
- `Gui.Mouse.Event` (`.cache/game/api/tealdef/api/gui.d.tl:228-258`): types `Pressed, Released, Clicked, Entered, Exited, Moved, Wheel, DoubleClicked, PressedOutside`, `button` 0 = left, 1 = middle, 2 = right, plus `x, y, xrel, yrel, handled`. **There is no Dragged type.**
- Seen in the Selector's `onProcessMouseEvent`: `Pressed`/`Released` (button 0) and `Moved`. `.cache/subscribed/zhenya_doubleclick_to_edit/content/gui/dce.script.lua:407-414` tracks `buttonDown` from Pressed/Released and acts on `Moved`. The overpass tool acts on `Released` + button 0 and returns `false` for the rest (`overpass_probe.script.tl:4484-4498`).
- **Unknown:** whether a left-button drag over terrain pans or rotates the camera in TF3 while a custom tool is active, and whether returning `true` from `onProcessMouseEvent` on `Pressed` stops that. The camera actions are `IA_CAMERA_PAN`, `IA_CAMERA_ROTATE_X`, `IA_CAMERA_TILT` (e.g. `.cache/game/base/content/gui/layers/layers_button_ridge.tl:65-66`), and their mouse bindings are not in the extracted files. Native brushes (terrain, asset) do paint while held, so the engine supports it for native actions.
- Cursor: `api.gui.mouse.getTerrainPosition() : Vec3f` ("last valid terrain position") and `hasTerrainPosition()` (`gui.d.tl:260-265`). The overpass tool reads them in `onHover` and in the mouse handler (4445-4460, 4494-4497).
- Engine selection highlight: pass transparent `selectionColor*` (`overpass_probe.script.tl:4500-4517`, "undocumented in SelectorParam.d.tl but the engine accepts them"; they are in fact declared in `builtin.d.tl:1402-1404`). Returning `true` from `onSelect` consumes the click so no entity window opens (4405-4430).
- `ActionDescriptorParam` (`builtin.d.tl:1338-1348`): `tool, layer, terrainCirclePolicy ("FocusSelection"|"Always"|"IfNoEntity"|"Never", 1331-1336), highlightedEntities, crosshair, parent, onBack, horizontalPromptList, children`. `mouseCursor` is passed by base code (`construction_react_util.tl:1420`) but not declared, so it needs a cast.
- The engine terrain circle (`terrainCirclePolicy`, Selector `circle*` colours) has **no radius field**, so it can't show our brush size.

## 3. Drawing the brush circle

- **Chosen: `builtin.EdgeRenderable{ edges = {...} }`** with `EdgeGeometry.Arc` pieces. This is verified in a shipped mod: `overpass_probe.script.tl:4532-4555` (full circle: `arc.center`, `arc.radius`, `startAngle = 0`, `angle = 2π`, `g.height = Vec2f(z, z)`, `g.width`, `g.length = 2πr`, `Edge.new(g)`, `colors = {c,c,c}`, `stepSize = 1`, `width = 1.5`, `offsetZ = 1.0`), added once as `children[#children+1] = builtin.EdgeRenderable{ edges = edgeBag }` (5043).
  - Types: `builtin.d.tl:46-56` (`Edge`: `geometry, colors, width, offsetZ, stepSize`), `EdgeRenderableParam{edges, ignoreDepth}` (1317-1320).
  - **Only one EdgeRenderable per recipe**: the engine asserts on more (overpass comment at 4517-4519, "the engine asserts on more than one builtin.EdgeRenderable per recipe").
  - Following hilly terrain: one arc has a single `height` pair (start/end), so split the ring into N arcs (e.g. 48) with heights from `api.engine.terrain.getHeightAt(Vec2f)` (`.cache/game/api/tealdef/api/engine.d.tl:1734`, accessor `terrain` at 1811; used in `.cache/game/base/content/game_mechanics/fun_elements/custom_entity_util.tl:74`). `ignoreDepth = true` keeps it visible through hills (needs a test).
- Fallback: `api.gui.mission.setZoneCircle(key, center, radius, draw, color, prohibitBuilding, playAnimation?, zOffset?)` (`gui.d.tl:704-713`) and `removeZone(key)`. This is a mission API: the base mission GUI script owns zones by key (`.cache/game/base/content/mission/mission_sim.script.tl:1085-1098`). It is not used per frame anywhere, and it needs `prohibitBuilding=false` and `playAnimation=false`. Use only if EdgeRenderable fails.

## 4. Finding what's under the brush

- `api.engine.util.octree.findEntitiesInCircle(center : Vec2f, radius, componentType) : {Entity}` (`.cache/game/api/tealdef/api/engine/util.d.tl:323-334`, accessor `octree` at 1054) and `findTransportNetworkNodesInCircle(center, radius) : {NodeId}` (335-339).
  - Base callers by type: `CONSTRUCTION` (`.cache/game/base/content/mission/tutorial/tutorial_story.tl:92`, `build_construction_variant.tl:60`), `BASE_EDGE` (`tutorial_story_util.tl:76`), `STATION`, `STATION_GROUP`, `CARRIAGE`, `VEHICLE_DEPOT`, `TOWN`, `TRANSPORT_VEHICLE` (`.cache/game/base/content/mission/name_util.tl:133-143`), `BASE_NODE` (`.cache/subscribed/parallel_tracks_1/content/parallel_tracks/parallel_tracks.script.lua:269`).
  - **Unknown:** whether the hit test uses the entity's position or its bounding volume, and whether `EDGE_OBJECT` is indexed. Edge objects are reachable anyway through `BaseEdge.objects` (`engine.d.tl:105`, `{{entity, EdgeObjectType}}`; `EdgeObjectType` = `STOP_LEFT, STOP_RIGHT, SIGNAL`, `type.d.tl:422-429`).
- ComponentType list (`engine.d.tl:1621-1684`): has `BASE_EDGE`, `BASE_EDGE_STREET`, `BASE_NODE`, `EDGE_OBJECT`, `CONSTRUCTION`, `TOWN_BUILDING`, `INDUSTRY`, `STATION`, `VEHICLE_DEPOT`, `PLAYER_OWNED`, `BRIDGE`. There is **no** `BASE_EDGE_TRACK` (track = `BaseEdge` without `BASE_EDGE_STREET`, or `BaseEdge.roadType`, `engine.d.tl:124-125`). There are **no** `BULLDOZER_INFO` or `BUILD_COST` component types: `BulldozerInfo.locked` / `BuildCost.bulldozeCost` exist as records (`engine.d.tl:247-260`) but can't be read through `getComponent`.
- `BaseEdge.type` is a `BaseEdgeType` = `NORMAL | BRIDGE | TUNNEL` (`type.d.tl:463-467`). The base bulldozer only removes underground objects in its "Underground" mode (`construction.tl:4050-4080`, `internal.css.lua:1033-1041`).
- Construction classification (`Engine.Component.Construction`, `engine.d.tl:295-335`): `frozenNodes, frozenEdges, depots, stations, industries, townBuildings, subconstructions, fileName, transf`. A town building is a construction with `#townBuildings > 0` and no stations, depots, industries or frozen network. That exact test is in `overpass_probe.script.tl:334-349` (`townBuildingConstruction`).
- Edge/node ownership by a construction: `api.engine.system.streetConnectorSystem.getConstructionEntityForEdge(e)` / `getConstructionEntityForNode(n)` (`.cache/game/api/tealdef/api/engine/system.d.tl:240,246`); `findSegmentsToDelete(con, keepIndustryRoads?)` (`engine/util.d.tl:827`) lists the street segments that go with a construction (base: `.cache/game/base/content/gui/main/industry_util.tl:563-570`).
- Ownership: `PLAYER_OWNED.player` ("can be bulldozed only by him", `engine.d.tl:854-859`); our player is `api.engine.util.getPlayer()` (`engine/util.d.tl:1023`). The headquarters is `PLAYER.headquarters` (`engine.d.tl:847-853`).
- `api.engine.system.streetSystem.getNode2SegmentMap()` (`system.d.tl:300`) returns the map for the whole world. Use it once per commit, if at all.

## 5. Removing things

- `api.type.SimpleProposal` (`type.d.tl:2827-2857`): `constructionsToRemove`, `streetProposal` (`SimpleStreetProposal`, 2764-2808: `nodesToRemove`, `edgesToRemove`, `edgeObjectsToRemove`, plus the add lists). "The proposal will take care of updating lines, stop, people and cargo" (2826).
- `api.cmd.makeWorldBuildProposalCmd(proposal | SimpleProposal, context, ignoreErrors, playerInitiated, doDust?)` (`.cache/game/api/tealdef/api/cmd.d.tl:952-962`) and `api.cmd.sendCommand(cmd, callback(data, success, resultEntities))` (598-600).
- Base removal code:
  - `industry_util.removeIndustries` (`industry_util.tl:560-601`): one `createProposalRemove(con, Context.new())` per construction, then **in the callback** `makeSegmentsRemoveProposal(segments)` for the attached roads. All are sent with `ignoreErrors=true, playerInitiated=false`.
  - Mission helpers remove constructions with `SimpleProposal{constructionsToRemove={e}}` + `makeWorldBuildProposalCmd(p, nil, true, false)` (`.cache/game/base/content/mission/tasks/bulldoze/auto_bulldoze.tl:16-22`, `mission_framework_util_entity.tl:123-129`).
  - Edges: `api.engine.util.proposal.makeSegmentsRemoveProposal(segments) : Proposal` (`engine/util.d.tl:934`; callers `industry_util.tl:584`, `.cache/game/base/content/mission/tutorial/tasks/tutorial_init.tl:127-133`, `map_editor.tl:1604`).
  - The player-facing mission task "bulldoze" doesn't remove anything itself: it waits for the player's native bulldozer apply event (`.cache/game/base/content/mission/tasks/bulldoze/bulldoze.tl:86`).
- **Preview/validation:** `api.engine.util.proposal.makeProposalData(proposal, context?) : ProposalData` (`engine/util.d.tl:925`). It returns `costs : integer` and `errorState{critical, messages, warnings, infos}` (`type.d.tl:2694-2760`). The overpass mod calls it with a **SimpleProposal** through a cast ("Build 40408 requires SimpleProposal here; the shipped Teal declaration says Proposal", `overpass_probe.script.tl:325-330`). Sign and meaning of `costs` for a pure removal: **unknown**.
- **Locks:** `api.cmd.makeWorldSetBulldozableCmd(entity, bulldozable)` (`cmd.d.tl:978-983`) is how missions lock things. Scripts can't read the lock (see §4), so we have to rely on the build refusing locked entities. Base removals use `ignoreErrors=true`. **Unknown** whether that bypasses a lock, so we send `ignoreErrors=false`.
- Refund: `bulldozeRefundTimeOut = 60.0`, `bulldozeRefundFactor = .75` (`.cache/game/base/content/base/mod.script.tl:30-31`). Whether a script removal with `playerInitiated=true` charges bulldoze costs, refunds and journals like the native bulldozer: **unknown**, check the finance window.
- Removing only a signal or waypoint (keeping its edge): no base or mod source does it. The overpass mod refuses to touch edges with objects (`overpass_probe.script.tl:457-470`, 872). **Unknown**, so it's a v1 non-goal: signals and stops go only together with their edge.
- **Trees / vegetation: no scripting API.** There's no command to remove assets or trees (full list `cmd.d.tl:613-1023`). Vegetation is erased only by the native asset brush with `eraseWhenEmpty = true` (`builtin.d.tl:352-372`; base tool `.cache/game/base/content/gui/construction/tools/vegetation_eraser_tool.script.tl:1-51`, `action = "ACTION_ASSET_BRUSH"`). Fields are similar (`removeField` cost in `mod.script.tl:33`, no script command). Point players at the base Vegetation Eraser.
- **Undo: none.** No `undo` or `IA_UNDO` anywhere in base content or the API.

## 6. Threads and where the code runs

- `getDefinition` and the custom-action recipe run in the GUI. `api.cmd.sendCommand`, `makeWorldBuildProposalCmd`, `makeProposalData`, `api.engine.getComponent`, `octree`, `terrain.getHeightAt` and `api.gui.mouse.*` are all called from there by the overpass tool (`overpass_probe.script.tl:1988-1992` "getDefinition runs on the GUI thread at tool open", 5501-5546 sends builds).
- **No game script is needed.** That means no `.gs.lua`, no saved state, and none of the guiHandleEvent subscribe pitfalls.
- Timing: use `os.clock()` like the overpass tool does. The recipe is on the GUI thread, so `api.util.getApplicationTime` would work here, but keeping to `os.clock` avoids the HUD-thread crash class (memory note).
- `getDefinition` may run in a different Lua state ("definition VM") from the one where `onChangeFn` and the recipe run ("the click runs in the GUI VM where rep lookups provably work … the definition VM that baked this param cannot enumerate the rep", overpass bridge picker, 5615-5622). The overpass tool does share file-level globals between `onChangeFn` and its build path (`g_selectedBridgeTypeIdx`), but it mirrors every change into recipe state with `fireReactEvent` so the recipe re-renders. Rules:
  - never compute in `getDefinition` anything the recipe needs at runtime;
  - push slider and checkbox values to the recipe with `fireReactEvent`, or read them with `getCurrentParams()`.

## 8. Phase 2 selection: API verified (2026-10-07)

Every read `bb_gather.tl` does, checked against `.cache/game/api/tealdef` (all "inferred" until TESTING §3 runs, except where a base or mod caller is named):

- `api.engine.getComponent<T>(Entity, ComponentType) : T` returns nil when the component is missing (`api/engine.d.tl:1686-1690`); `entityExists` (`:1723`). Teal can't infer `T` through `pcall`, so `bb_gather` wraps it in a closure returning `any`.
- `Engine.Component.BaseEdge` (`api/engine.d.tl:99-130`): `type : BaseEdgeType`, `objects : {{Entity, EdgeObjectType}}`, `node0/node1`, `position0/1`, `tangent0/1` (Vec3f). Tunnel test `be.type == api.type.enum.BaseEdgeType.TUNNEL` (`api/type.d.tl:463-467`, enum accessor `:2120`; same pattern `overpass_probe.script.tl:454`).
- Street vs track: presence of `BASE_EDGE_STREET` (`api/engine.d.tl:1626`, record `:147`). There is no track component.
- `Engine.Component.Construction` (`api/engine.d.tl:295-335`): `transf : Mat4f`, `stations`, `depots`, `industries`, `townBuildings`, `frozenNodes`, `frozenEdges`. Origin via `Mat4f:getTransl() : Vec3f` (`api/type.d.tl:783`; base `celebrations.script.tl:211`, `tutorial_story_util.tl:246`).
- `PlayerOwned.player` (`api/engine.d.tl:855-860`), `Player.headquarters` (`:847-853`; base read `game_tooltips.tl:67`, `town_util.tl:1924`), `api.engine.util.getPlayer()` (`api/engine/util.d.tl:1023`).
- `streetConnectorSystem.getConstructionEntityForEdge/ForNode/ForSubconstruction` (`api/engine/system.d.tl:240, 246, 249`); `-1` when none (base checks `>= 0`, `industry_util.tl:564`; `dce.script.lua:28`).
- **Industry roads.** `api.engine.util.construction.findSegmentsToDelete(con, keepIndustryRoads = false)` (`api/engine/util.d.tl:823-827`) lists the street segments the base removes together with an industry (`industry_util.tl:563-570`). These are town-style roads, not frozen edges, so `getConstructionEntityForEdge` alone would not protect them. `bb_gather` runs it for every industry construction the wide query finds and also treats an unowned street ending on a node frozen in an industry (`getConstructionEntityForNode`) as an industry road.
- `api.engine.util.octree.findEntitiesInCircle` (`api/engine/util.d.tl:323-329`): its doc only says "entities in given radius". Hit semantics are still unknown (TESTING §2), hence `EDGE_MARGIN` (`bb_brush.tl`) and origin-only construction hits (`bb_select.CONSTRUCTION_ORIGIN_ONLY`).
- `ActionDescriptorParam.highlightedEntities : {Engine.Entity}` (`base/tealdef/scripts/builtin.d.tl:1338-1348`); the base passes entity lists there in line management (`line_util.tl:1182`). The highlight colour is the engine's; our Selector's selection colours stay transparent. Whether those colours also tint `highlightedEntities` is unknown (TESTING §3).
- Hermite edge curve: the engine stores an edge as end positions + tangents; for a straight edge the tangents equal the chord. The touch test samples `p(t) = h00·p0 + h10·t0 + h01·p1 + h11·t1` at 9 points and measures polyline distance, with a cheap reject from the Bezier hull `p0, p0 + t0/3, p1 − t1/3, p1`.

## 9. Phase 3 commit path: API verified (2026-10-07)

All "inferred" until TESTING §4-6 run, unless a base or mod caller is named.

- **Filling a SimpleProposal from script.** `api.type.SimpleProposal.new()` comes with an empty `streetProposal`; the lists are set by **assigning a whole Lua table**: base `auto_bulldoze.tl:19` / `mission_framework_util_entity.tl:91,125` (`proposal.constructionsToRemove = {entity}`), base `electrify.tl:24` (`proposal.streetProposal.edgesToRemove = {entity}`), Overpass `overpass_probe.script.tl:1537-1538, 2794, 3304`. The userdata setter **copies** the table, so appending after the assignment is lost (Overpass comment `overpass_probe.script.tl:3403-3409`). `bb_commit.buildSimple` builds each list first, then assigns once.
- **No base code removes edges with a bare `edgesToRemove` SimpleProposal.** Base removals of edges go through `api.engine.util.proposal.makeSegmentsRemoveProposal(segments) : Proposal` (`engine/util.d.tl:934`; `industry_util.tl:584`, `tutorial_init.tl:127-133`, `map_editor.tl:1604`), and constructions are removed **first**, with the edges sent **in the callback** (`industry_util.tl:560-601`). Electrify removes + re-adds in one SimpleProposal (`electrify.tl:24-25`). The Overpass KB warns that replacing an edge with `BaseEdge.objects` without migrating them leaves dangling refs and a delayed `AreAllNodesEmpty` crash (`overpass_probe.script.tl:457-470`). Hence **default = base two-step** (`bb_commit.COMBINED_PROPOSAL = false`): constructions in a `SimpleProposal{constructionsToRemove}`, then the edges with `makeSegmentsRemoveProposal` (the engine builds node/object removal itself). `true` switches to the PLAN's single SimpleProposal with `edgesToRemove` + `edgeObjectsToRemove` (from fresh `BaseEdge.objects`) + `nodesToRemove` (orphans, below).
- **Orphan nodes** (combined mode only): degree per end node from `streetSystem.getNodeSegments(node)` (`engine/system.d.tl:309`, used by Overpass `findConnectedEdges`, `overpass_probe.script.tl:442-445`) instead of the world-wide `getNode2SegmentMap()`. A node goes into `nodesToRemove` only if every incident edge is removed and `getConstructionEntityForNode(node) < 0`; an unreadable owner counts as frozen. Overpass refuses the same "node removed while an unchanged edge still uses it" case (`overpass_probe.script.tl:3553-3567`).
- **makeProposalData.** Declared `(proposal : Proposal, context? : Context)`; it accepts a SimpleProposal through a cast (Overpass `overpass_probe.script.tl:325-330`). `ProposalData.costs : integer` and `errorState{critical, messages}` (`type.d.tl:2694-2760`). The base buy check treats `costs > balance` as "Not Enough Money" and shows `errorState.messages` as display text (`bridge_and_tunnel.tl:132-150`). Sign for a removal: still **unknown**; `bb_commit` refuses only when `costs > 0 and costs > balance` and logs the raw value.
- **Command and callback.** `makeWorldBuildProposalCmd(p, ctx, ignoreErrors, playerInitiated, doDust?)` (`cmd.d.tl:960-961`; the doc comment lists doDust before playerInitiated, the signature and base callers put it last: `industry_util.tl:586,593`). `sendCommand(cmd, callback(data : WorldBuildProposalCommandData, success : boolean, resultEntities))` (`cmd.d.tl:591-600`); **success is the 2nd argument**; `data.resultProposalData.errorState.messages` holds the reasons (`cmd.d.tl:510-525`). The callback runs in the **GUI VM**: base calls `api.gui.construction.updateRefundableEntities` inside it (`bridge_and_tunnel.tl:195-204`) and Overpass sets react state from it (`overpass_probe.script.tl:5546-5577`). ## 10. Toolbar: buttons side by side and a live status (2026-10-07, user request after the first in-game look)

The first in-game screenshot showed the one-value **Bulldoze selection** button as a full-width blue button with its label clipped, and the user asked for **[Bulldoze] [Clear]** side by side plus the current selection in the panel instead of the cursor tooltip. Evidence (paths under `.cache/game/base/content/gui/` unless stated):

- **How the bar is built.** Toolbar params are the definition's `params` with `location = Toolbar` (`construction/construction.tl:1747`). `ConstructionParamsContent` walks them and groups consecutive params: a new group starts when `group` or `vertical = not hideLabel` changes; each group is one `Component!param-group` with a **horizontal** BoxLayout when `hideLabel` is set and a vertical one otherwise; a *named* group gets a separator image before it when a group precedes it (`construction/construction.tl:2024-2074`). So **two hideLabel Buttons with the same `group` sit side by side**. Verified in a shipped mod: the Overpass Builder's two preset IconButtons share `group = "presets"` + `hideLabel` "so they render side-by-side as a single row" (`.cache/subscribed/move_it_probe_overpass/content/tools/overpass_probe/overpass_probe.script.tl:5677-5715`). Base uses `group` for its toolbar rows too (`construction/construction_react_util.tl:1949-1997` "resources", `:660` "undergroundMode").
- **Why the label was clipped.** In the bottom bar every button TextView that is a direct child of the button's layout is fixed to 50 × 24 px: `R::ConstructionParamsContent !construction-menu-bottom-bar-params-content ToggleButton > FloatingLayout > TextView { size = {50, 24} }` (`construction/construction.css.lua:820-823`). The panel is 314 px wide with 8 px side padding (`construction.css.lua:723-727`). The Overpass mod hit the same overflow and switched its presets to icons (`overpass_probe.script.tl:5684-5686`).
- **Button content can be ours.** `ConstructionMenuParam.makeCompactButtonFn(value) : TreeNodeId` (`construction/construction_menu.d.tl:78`) is copied into the UI param (`construction.tl:1027-1039`) and, for `uiType = Button`, replaces the default TextView: `button = { content = scriptParam.makeCompactButtonFn(value) }` (`main/script_param_util.tl:403-405`); a one-value Button becomes a single `ToggleButton{content = …}` (`script_param_util.tl:457-469`). A BoxLayout around the TextView escapes the 50 px rule (it only matches a *direct* TextView child) and is centred by `ToggleButton > FloatingLayout > * { gravity = {0.5, 0.5} }` (`main/builtin.css.lua:178-182`). Base precedents for non-TextView content: a recipe returning a BoxLayout as Button content (`line_vehicle_mgmt/cargofilter_window.tl:151-163`, `IconLabelIndicator` → `main/gui_react_util.tl:330-332`, which returns a BoxLayout), a BoxLayout as content (`menu/mod_manager_react_util.tl:629`).
- **Names, values and tooltips are static.** The bar re-renders a param only when its copied UI fields or its value change (`construction.tl:1072-1091`, deepEquals per step); `formatValueFn` (`script_param_util.tl:109-110`) is evaluated only on such a re-render. There is no text/label `ScriptParamType` (`Button, Slider, ComboBox, IconButton, CheckBox`, `api/tealdef/api/type.d.tl:1961-1967`), and the Overpass author notes the panel "can't show dynamic text" and shows build errors as pre-baked **disabled** Buttons toggled by `checkEnabledFn` (`overpass_probe.script.tl:246-252`, `6080-6098`).
- **`checkEnabledFn` runs every step** (`construction.tl:1584-1597`, called from `onStep` `:1901-1925`); `"Disabled"` renders the param with `enabled = false` (`construction.tl:2059-2062`): grey background, dark text (`main/builtin.css.lua:248-251, 268-275`), not clickable.
- **Same Lua state.** The menu loads `getDefinition` through `util.useFn` (`construction/construction_react_util.tl:2829-2831`), which resolves the function in the already-loaded `game` script table (`scripts/util.tl:5-27`); the definition's closures (`onChangeFn`, `checkEnabledFn`, `makeCompactButtonFn`) and the custom-action recipe come from that one module instance. The Overpass mod relies on this: its recipe writes `g_overpassReadyToBuild` (`overpass_probe.script.tl:4123-4128`) and its Build button's `checkEnabledFn` reads it (`:6125-6127`); the recipe also calls the menu API it captured in `onChangeFn` (`:4177-4180`).
- **Stored toolbar values are per session, per category.** The menu keeps changed values in a `useRef` per category (`construction.tl:1454`, written in `changeParam` `:1866-1886`) and resets them only for params with `resetOnCategoryChange` / `resetOnMenuClose` / `resetOnDefinitionChange` (`:1786-1834`). A CheckBox with no stored value shows `defaultIndex` (`getParamDefaultValue`, `construction.tl:946-965`; widget value = stored − 1, `script_param_util.tl:526-530`).

**Chosen mechanism.**

1. **[Bulldoze] [Clear]**: two one-value `Button`s with `hideLabel = true` and the same `group` (`bulk_bulldozer_actions`). Labels "Bulldoze" / "Clear" come from `makeCompactButtonFn` as `BoxLayout{ TextView }`, so they are not clipped. Clear fires `BulkBulldozer.clear` → the recipe's `cancelPending` (same path as RMB).
2. **Status chip**: a third one-value Button under them (no `group`, so no separator between the buttons and the chip), `checkEnabledFn → "Disabled"` (the Overpass "status as disabled button" pattern), whose `makeCompactButtonFn` returns our own `BulkBulldozerStatus` recipe. That recipe returns a vertical BoxLayout of two TextViews (headline "12 selected · $34,500", detail "8 roads · 3 tracks · 1 asset") and **re-renders itself**: it polls a module-level `g_status` (written by the action recipe whenever the text changes, version-stamped) on `onStep`, and also takes the same text from a `BulkBulldozer.status` react event, so it still updates if the two ever turn out to live in different Lua states. Text building is pure (`bb_status.tl`, clipped to 36 characters per line).
   - Rejected: a dynamic `formatValueFn` (the bar doesn't re-render for it), mutating `values` at runtime (relies on the menu's deepEquals of a table we'd swap), a separate window (window crash notes: frame min height, position restore) and an `ActionTooltip` (the user wants the panel).
   - Memory checks: the recipe returns a layout (BoxLayout), it is not used as `Component{layout = …}`, no ImageView fields, GUI thread only (construction menu recipe).
3. **Town roads ✔ in the screenshot**: not a definition bug. `defaultIndex` is 1 (off) for Town roads (`sel.defaultFilters`, tested in `test_definition.lua`), and the menu shows `defaultIndex` when nothing is stored. The tick means the CheckBox was toggled earlier in that game session (values persist per category for the session, see above; Road → Tools and Rail → Tools are separate categories). The log confirms it: `filter event: townRoads = true` or `filters {…townRoads…}` on activation.

Unverified until the next in-game look (TESTING §1): the chip's readability when disabled, whether 36 characters fit, and that the recipe-as-button-content renders (base does it for `Button`, ours is a `ToggleButton`; `builtin.css.lua:186` has a rule for `ToggleButton > FloatingLayout > R::Component > BoxLayout`, so recipe content is expected there).

## 11. Selection highlight: why nothing showed, and the fix (2026-10-07, user report)

In game the selection was counted in the status chip ("20 roads") but **nothing was highlighted in the world**. The recipe passed `highlightedEntities = sel.entities(stroke)` on the ActionDescriptor and gave its Selector transparent `selectionColor` / `selectionOutlineColor` / `selectionOutlineColor1` (copied from the Overpass tool, which only wanted to hide the hover tint, `overpass_probe.script.tl:4500-4517`). Evidence (paths under `.cache/game/base/content/` unless stated):

- **The engine has no separate highlight colour.** `ActionDescriptorParam` (`scripts/builtin.d.tl:1338-1348`) has `highlightedEntities` but no colour field; the only selection colours anywhere are the Selector's `selectionColor`, `selectionOutlineColor`, `selectionOutlineColor1` (`scripts/builtin.d.tl:1402-1404`). The circle colours (`1406-1410`) are for the terrain circle only.
- **The only base caller of `ActionDescriptor.highlightedEntities`** is the line manager (`gui/line_vehicle_mgmt/line_util.tl:1182`; callers `manager_window.tl:435, 817, 992, 1157, 1308` pass the *selected vehicles*). It passes the same list to a `LineVehicleColor` colour pass (`line_util.tl:1050-1052`, `api/tealdef/api/type.d.tl:4526-4535` "Specify specific entites to apply an highlight effect to") and sets **non-transparent** Selector colours in the same descriptor (`line_util.tl:1157-1159`, `1241-1243`: inverted = black outline). So the highlight is drawn with the Selector's colours; ours were alpha 0, hence invisible. **Inferred** (no base code highlights edges or constructions this way; confirm in game).
- **Selector colours drive the hover effect too.** The base defaults are `selectionColor = invisible` (no fill) and `selectionOutlineColor = white` (`gui/main/selection_colors.gres.lua:7-8`), used as outline at `transparency.Low` = 0.75 and outline1 opaque (`gui/main/selector_react_util.tl:94-96`, `gui/construction/construction_react_util.tl:1378-1380`). That white outline is the "default white hover highlight". The Overpass comment says it appears "on network nodes and segments", so the effect does apply to **edges** (`overpass_probe.script.tl:4500-4504`). Constructions and town buildings get it in the default selector (entity windows), whose filter rejects only BASE_EDGE (`selector_react_util.tl:145-147`).
- **The native bulldozer's red "will be removed" tint is engine-internal.** `ConstructionAction.Bulldozer` takes only `undergroundMode`, circle and crosshair colours (`scripts/builtin.d.tl:390-410`); the base sets only `circleBorderColor` from `constructionColors.Bulldozer` = gold (`gui/construction/construction_react_util.tl:3574-3582`, `construction_colors.gres.lua:12`). No script-side red to copy. Closest base palette reds: `default_colors.gres.lua:53` Error = fireEngineRed `#CE2029` and `:59` Negative = lightCoral `#F08080` (`gui/main/color_internal.lua:129, 134`).
- **Overlay fallback is a verified shape.** `EdgeGeometry` has `straight` / `arc` / `cubicSpline` (`api/tealdef/api/type.d.tl:1030-1096`); the Overpass tool draws `EdgeGeometry.Straight` pieces and full-circle Arcs in its single EdgeRenderable bag (`overpass_probe.script.tl:4831-4846`, `4532-4555`), and only one EdgeRenderable per recipe is allowed (`:4517-4519`).

**Fix (`bb_highlight.tl`, constant `MODE`, default `"both"`):**

1. **Engine tint:** the Selector gets the base-palette red: fill `#CE2029` α 0.45, outline α 0.75, outline1 α 1. During the hover preview (nothing selected yet) it uses lightCoral at lower alpha, so "what the brush would take" reads lighter than the real selection.
2. **Hover only on highlighted objects** (`HOVER_ONLY_HIGHLIGHTED = true`): the Selector `filter` accepts only entities in the highlight set, so the hover effect (same colours) never lands on an object that is not selected or previewed. Clicks keep working: LMB/RMB are handled in `onProcessMouseEvent`, which already works over open terrain where no entity is hovered.
3. **Overlay lines:** a red line along each selected edge (Hermite curve in x/y **and z** cut into ~15 m straight pieces, max 8 per edge, offsetZ 1.5 m) and an 8 m red circle on each selected construction's origin, in the same EdgeRenderable as the ring (`ignoreDepth = true`). At most `MAX_SEGMENTS` = 1600 pieces: over budget every edge gets fewer pieces first, then trailing edges are dropped (logged once per selection). Built once per selection change and cached; the ring still re-renders on cursor moves.

`MODE = "engine"` = tint only (transparent-free Selector, no lines), `"lines"` = lines only (Selector transparent again, as rev 1). The active mode is logged on tool activation (`highlight mode both (...)`).

## 12. In-game feedback round (2026-10-07): one Roads filter, right click, clear on close

**Roads.** There is no field that tells a town road from an unowned player road: both are streets without `PLAYER_OWNED`, and streets freed from a street construction (e.g. a roundabout) lose it too. User decision: one **Roads** kind/filter (default on) for every street that is ours or unowned. The hard rules still keep out another player's streets (`owner >= 0 and ≠ us`), streets that belong to a construction (`getConstructionEntityForEdge >= 0`) and industry roads (`findSegmentsToDelete(industry, false)` and unowned streets ending on an industry-frozen node). New CheckBox key `bulk_bulldozer_f_roads` so the remembered values of the old two keys don't carry over.

**Right click: root cause, from the game log** (`crash_dump/stdout.txt`, 2026-10-08 01:20:25-26 UTC). One RMB click with a selection waiting logged only

```
mouse PressedOutside button=2 handled=false -> return false (phase selected)
mouse Clicked button=2 handled=false -> return false (phase selected)
```

and no `Pressed button=2` / `Released button=2` at all in the session (all 16 `Pressed` and `Released` are button 0). The handler cleared only on RMB `Pressed`, so it never ran. Button numbering is right (`gui.d.tl:246`: 0 left, 1 middle, 2 right). Where the press goes: the player's bindings (`settings_keys_v3.lua`) put the right button (SDL `mouseButton = 3`) on `IA_MENU_BACK`, `IA_BACK`, `IA_CLOSE_TOPMOST_WINDOW` and `IA_CONSTRUCTION_ACTION_CANCEL`, so the press is taken before the Selector's `onProcessMouseEvent` (the camera may take it too; the `Exited` events in between suggest a capture). `ActionDescriptor.onBack` (already wired to clear) never fired either (no `(back)` line), and neither did the conditional `IA_MENU_BACK` handler (no `(Esc)` line). The Selector filter (`HOVER_ONLY_HIGHLIGHTED`) doesn't matter here: `PressedOutside`/`Clicked` arrive over open terrain like LMB does.

**Fix:** RMB `PressedOutside` (or `Pressed`) records the screen position; RMB `Clicked` (or `Released`) clears a pending selection unless the mouse moved more than `RMB_CLICK_MAX_PX` = 16 px since the press (a camera drag). Every RMB release logs `right click (Clicked): moved N px -> clear` / `... selection kept` / `nothing selected`. onBack and the Esc handler stay.

**Clear on close: why the selection survived.** In the same log a 7-object selection made at 01:21:00 was still there at 01:22:02 after another tool built something (`No construction entity created!` at 01:21:47), and **no `tool deactivated` line appears in the whole session**: the recipe stayed mounted and its `onStep` never saw `isActive == false` (a hidden menu tab is most likely not stepped; `construction.tl:425-436` aborts from `onStep` too). The selection lives in recipe refs, and `g_status` (status chip) at file scope, which survives an unmount.

**Fix (layered, each logged):** (1) recipe `react.onMount` / `react.onUnmount` reset the selection and `g_status` (base pattern `construction_react_util.tl:1355-1364`); (2) a render with `isActive == false` after an active one clears at once; (3) the world layer (`actionFn`) registers its own mount/unmount: the menu swaps the action to another entry's or its `"default"` when the tool is left (`construction.tl:4489-4501`); an unmount not followed by a mount within `LAYER_GONE_SECONDS` = 0.25 s (os.clock) clears, checked in `onStep` and again when the layer mounts (a same-frame re-binding does not clear). A timer ("no onStep for 5 s") was tried and dropped: it could clear an idle selection while the game window is unfocused. A running commit keeps going in the engine; its result is just not shown.

**Toolbar sync (safety fix).** The log shows `getCurrentParams {}` on activation and on every radius event, so the recipe could start from the defaults while the toolbar showed a box the player had toggled (e.g. Roads unticked → roads still taken). The values the toolbar shows reach Lua in two places: `checkEnabledFn(params)` is called with the toolbar's params on every activation and change (`updateDisabledParams`, `construction.tl:1584-1596`, called from `setCurrentParams` 1650-1653 and `changeParam` 1890), and `onChangeFn(newValue, menuApi, old)` with `menuApi.getCategory()` / `getCurrentParams()` (`construction_menu.d.tl:33-45`). Values: 2 = ticked, 1 = unticked (same storage as `onChangeFn`, `changeParam` 1866-1897); anything else = unknown. Both feed file-scope `g_filterMem` (shown values + toggles per category), which is **not** reset on mount/close, like the menu's own memory (`refStoredParams`); the status chip's `checkEnabledFn` fires `BulkBulldozer.shown` for the recipe in case it runs in another Lua state. `bb_select.resolveFilters`: shown value if known; else the default when no toggle of that field was seen in any category or all seen toggles equal the default; else OFF, logged as `unknown, treated as off`.
