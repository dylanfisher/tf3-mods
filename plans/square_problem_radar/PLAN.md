# Problem Radar (`square_problem_radar`): plan

A problem radar for TF3. It packs every current problem in your transport network into one dense, sortable window. When nothing is wrong, it stays quiet.

**Status (2026-10-07):** phases 1-5 are implemented, the phase 6 review fixes are applied (see Phase 6), alert smoothing is added (see "Smoothing") and phase 7 adds the **Economy** tab (`line_unprofitable`, `line_low_use`; state v6). Offline: `make check`, `make test` (182 tests) and `make validate` pass. Phase 7 perf review applied (2026-10-07, see Phase 7). Verified in game: the phase 1 UI, adding the mod to an existing save, and Phase 7's `line_unprofitable` rows. **Remaining:** the in-game checklist (`TESTING.md`, one ordered list for the finished mod), threshold tuning, the 1920×1080 `_metadata/0.png` preview, and upload (Mod Hub → My Mods; bump `revision` with every later update).

## Decisions (interview, 2026-10-04)

| Topic | Decision |
|---|---|
| Core goal | Problem radar: alerts first, quiet when healthy. Not a general stats dashboard. |
| Presence | HUD setting chooses between **(a)** an always-on compact HUD panel or **(b)** a small badge (e.g. `● 3`) that expands into the full window. |
| Base-game alerts | **Aggregate + add.** List problems the game already flags *and* our own checks. Send our own notifications only for problems the game doesn't announce itself. |
| Notify level | Configurable per alert type: `off` / `passive` (listed only) / `notify` (toast when it first appears). |
| Stuck rule | Smart defaults: game flags (`Blocked`, `NoPath*`) count immediately; otherwise not moving for X game-minutes while en route and away from a stop. Excludes user-stopped vehicles and ships queueing at a harbour. One adjustable threshold per carrier. |
| Line checks | Broken / no path, capacity mismatch, bunching / gaps. (Unprofitable: **not** wanted.) **2026-10-07: reversed** by the user: lines that consistently lose money over the last year, or run at very low utilisation over about a year, are flagged in a new Economy tab; bigger losses / lower use = higher tier (Phase 7). |
| Extra checks | Overcrowded stations, old / worn vehicles, idle in depot (incl. lines with no vehicles). |
| Layout | Tabs: **All** (sorted by severity) · **Vehicles** · **Lines** · **Stations** · **Fleet** · **Economy** (Phase 7) · **Settings**. Each tab label carries its count. |
| Severity | 3 tiers, colour-coded. The badge/HUD shows the worst tier. |
| Row action | Jump camera + open the game's own entity window. (No snooze, quick fixes or inline breakdown in v1.) |
| Settings | In-window **Settings** tab, saved per savegame. |

## Alert catalogue

| ID | Tab | Tier | Source | Base game already notifies? |
|---|---|---|---|---|
| `veh_blocked` | Vehicles | Critical | `getVehicleProblems()`: `Blocked` | yes (vehicle warning) |
| `veh_nopath` | Vehicles | Critical | `getVehicleProblems()`: `NoPath*` (ship-specific `NoPathShip`), `getNoPathVehicles()`, reason via `getFailedPathReason` | yes |
| `veh_stuck` | Vehicles | Critical | inferred: speed 0 ≥ threshold, `EN_ROUTE`, not `userStopped`, not approaching a station | partly (5 min, all carriers) |
| `train_blocked_by` | Vehicles | Warning | `landVehicleMoveSystem.getBlockedTrains()` (blocked → blocker pair, both clickable) | no |
| `line_broken` | Lines | Critical | `getLineProblems()` / `getProblemLines()`: `NO_PATH`, `ZERO_OR_ONE_STATION`, `INCOMPATIBLE_STATIONS`, `DOUBLE_STATIONS`, `BAD_ALTERNATIVE_TERMINAL`; path-break position from `PathProblemLocation` | yes (line warning) |
| `line_no_vehicles` | Lines | Critical | `#getLineVehicles(line) == 0` with ≥ 2 stops | partly |
| `line_cargo_issue` | Lines | Warning | `getLinesIssues()`: nowhere to load/unload, vehicle useless | yes |
| `line_cargo_not_unloaded` | Lines | Warning | `simEntityAtVehicleSystem.getVehiclesWithRoundTripCount()` (vehicle → cargo count), grouped per owned line via the scan's `getLineVehicles` lists; one row per line, metric `N veh · cargo` | yes (`cargo_rtc_warning` "Cargo Not Unloaded", per vehicle, initially ignored: HUD/LVM icons only) |
| `line_overloaded` | Lines | Warning | waiting at the worst line stop (`getLineStopSimEntitiesCount`) ÷ one vehicle's capacity (`getLineCapacityUsages` ÷ vehicles), sustained | no |
| `line_underused` | Lines | Info | `getLineCapacityUsages()` used/capacity (the base "Utilization") below threshold, sustained | no |
| `line_bunching` | Lines | Warning | headways from `lineStopDepartures` vs the base line "Frequency" interval (`1 / getMaxFrequency`), sustained (our metric) | no |
| `station_overcrowded` | Stations | Warning | `calculateStationGroupCargo(sg, -1).overflow > 0` | yes |
| `station_useless` | Stations | Info | `getLineStationProblems()` | yes |
| `fleet_worn` | Fleet | Info | `getVehicleMaintenanceState(v) ≤ threshold` | yes (≤ 0.2) |
| `fleet_old` | Fleet | Info | age > lifespan (`vehicle_util.getAge` pattern) | no |
| `fleet_idle_depot` | Fleet | Info | `IN_DEPOT` with `daysInDepot ≥ N` | no |
| `line_unprofitable` | Economy | Info → Critical (cost coverage + size of the loss vs all lines' costs) | `finance.calculateBalance({line}, …)`: 12-month balance < 0 and ≥ 3 of 4 quarters < 0 (Phase 7) | no |
| `line_low_use` | Economy | Info → Critical (by average) | our time-weighted yearly average of `getLineCapacityUsages` used/capacity (Phase 7) | no |

"Base game already notifies? = yes" means the default for our toast is `passive`, so it doesn't duplicate the game. Every other row defaults to `notify` for Critical, `passive` otherwise.

## Architecture

```
content/radar/
  radar.gs.lua             registers update/handleEvent
  radar.script.tl          engine side: staggered scans, stuck timers, settings, notifications
  radar_checks.tl          pure check functions (input: plain tables → output: alerts). Unit-tested.
  radar_types.d.tl         Alert, Settings, ScanSnapshot types
  gui/
    radar_hud.res.lua      react-plugin ::MainModButtonAreaExtension
    radar_hud.script.tl    HUD/badge + window recipe (TabWidget + DataTable per tab)
    radar_hud_model.tl     view model: sorting, counts, worst tier, row formatting. Unit-tested.
    radar_hud.css.lua      tier colours, density
  notify/
    radar_notification.res.lua / .script.tl
tests/square_problem_radar/test_checks.lua, test_hud_model.lua
```

- **Engine script (`update`)** owns anything that needs memory across ticks:
  - per-vehicle "first seen stopped" time, for `veh_stuck`;
  - the "alert first seen" set, so a toast fires only once per new alert;
  - line-quality sustain timers and the rotating line cursor (Phase 4);
  - settings.

  It staggers the work across ticks like the base notifications script (slice by `tickCount % 4`) and writes a compact alert list into game-script state.
- **GUI** reads that state via `getEntityForGameScript` + `GAME_SCRIPT` component with `useStepStateTimer(…, 1.0)`. It never scans the world itself. Settings changes go back as `makeScriptingSendEventCmd` events.
- **Row click**: `api.gui.camera.focusEntity(e)` + `fireReactEvent("selectEntity", {entity = e, stack = true})`. For path problems, `focusPosition(pos)` goes to the break location instead.
- Patterns come from an earlier mod in this workspace (ridge plugin, singleton window, notification type, model/test split) and the base game sources cited in each file.

## Alert row format (dense)

```
●  STUCK      Ship  "Harbour Ferry 3"   Line 7 Coastal   12m standing   NoSmallShip @ waterway
●  NO PATH    Line  "R2 Northern"       stop 4→5        missing catenary
◐  BUNCHING   Line  "Bus 14"            3 of 5 vehicles within 40 s   target 2:30
○  WORN       Bus   "Bus 14 #2"         18% condition    age 21/20 y
```
Columns: tier · type · entity (clickable) · context (line/stop) · key metric · detail. Sortable; default sort is tier, then age of alert.

## Phases

1. **Skeleton + UI proof:** ridge button that opens an empty tabbed window; HUD-mode setting toggles badge vs compact panel. This closes the riskiest unknown (rendering in the ridge slot) first.
   **Status: done, verified in game (2026-10-05)**: the ridge button renders, the window opens, tabs and the HUD-mode toggle work and persist, and adding the mod to an existing save works. Not yet checked: removing the mod from a save, and achievements staying enabled (TESTING.md §8-9). The off-centre window bug is fixed in phase 2: the window now has an id and is centred by CSS `gravity`/`anchorPoint`, like the base finance/company windows.
2. **Game-flag alerts:** `veh_blocked`, `veh_nopath`, `line_broken`, `line_no_vehicles`, `line_cargo_issue`, `station_overcrowded`, `station_useless`, `fleet_worn`. These are pure reads of the game's verdicts.
   **Status: implemented; offline tests pass; needs in-game verification (TESTING.md §3).**
   - Pure checks live in `radar_checks.tl`. The engine's gather layer (`radar.script.tl` `scan*`) makes every `api.*` call, and each scan is wrapped in `pcall`.
   - Scans are staggered: one of 4 groups (lines, stations, vehicles, fleet) runs every 3 sim updates, so a full refresh takes about 2.4 s. While paused they run on `tickCount` with slots 15 apart.
   - State v2 is `{version, settings, alerts ≤ 300, total, kindCounts}`. v1 is migrated. `state:set` is called only when something changed.
   - Alerts are language-neutral (codes plus game names). The GUI model translates them, reusing the base notification wording.
   - `line_no_vehicles` is suppressed while the same line is `line_broken`.
   - `station_useless` is sourced from `getLineStationProblems()` as the catalogue says. That is the base "line station warning" (stop unusable for the line's vehicles). The base "Station Not Functional" notification (no catchment) is a different check and is not included.
3. **Inferred alerts:** `veh_stuck` with per-carrier thresholds and harbour exclusion, `train_blocked_by`, `fleet_old`, `fleet_idle_depot`.
   **Status: implemented; offline tests pass; needs in-game verification (TESTING.md §3, §10).**
   - **Stuck timer: our own, not `MOVE_PATH.dyn.timeStanding`.** No base script, official mod or wiki page reads `timeStanding`. It appears only in `engine.d.tl:686` and the model-animation `VehicleScriptingInfo` (`type/transformator.d.tl:226`), with no unit or reset rule documented. It also exists only on `MOVE_PATH`: ships and aircraft move on `MOVE_PATH_AIRCRAFT`, which has no such field. So we time it like the base stuck rule (`notifications.script.tl:539-575`, `vehicle2problem[v].problemSince`). `state.memory.stoppedSince[v] = gameTime` while the vehicle is owned, `EN_ROUTE`, not `userStopped` and `getSpeed <= 0.01`. Entries are dropped as soon as the vehicle moves or is gone, and capped at 500 (oldest kept).
   - Thresholds are settings (`stuckMinRoad/Tram/Rail/Water/Air`, game-time minutes, defaults 3/3/5/10/5, range 1-240) and `idleDepotDays` (default 30, range 1-3650). They're validated in `radar_settings.tl` (`NUMBERS`, `KEYS`, `STUCK_KEYS`) and settable today via `ProblemRadar.setSetting`; the UI comes in phase 5.
   - **Exclusions** (checked only once a vehicle is over its threshold, because `MOVE_PATH` copies the whole path):
     - vehicles already in `veh_blocked` / `veh_nopath`;
     - `MOVE_PATH.dyn.approachingStation`;
     - ships: `MOVE_PATH_AIRCRAFT.shipState.dyn.approachingStation`, or `shipState.waitingDist > 0 and not clearToLand` (harbour queue);
     - aircraft: `aircraftState.waitingDistance > 0`;
     - trains in a `getBlockedTrains` pair, which go to `train_blocked_by`.

     Semantics come from field names only, since no base code reads them. In-game check: TESTING.md §10 (harbour / runway queue fields).
   - Trains with `isTrainWaitingForFreePath` past the rail threshold but with no blocker pair become `train_blocked_by` with code `WaitingForPath` (no `entity2`).
   - **`train_blocked_by`:**
     - Pairs from `landVehicleMoveSystem.getBlockedTrains()` are timed per blocked train in `memory.blockedSince` / `blockedBy`. The timer restarts when the blocker changes. The cap is 200.
     - A pair counts after the rail threshold.
     - Chains collapse to one row per root, the train at the head that nothing blocks; in a cycle the root is the cycle's lowest id. The row's entity is the longest-waiting train directly behind the root, `entity2` = root, and the metric is `"20m +2"` (+N more trains in that queue).
     - Deadlocks the game flags (`veh_blocked`) are excluded. A `→` button next to the row (also on `veh_blocked` rows) jumps to `entity2`.
   - **`fleet_old`:**
     - Mirrors `vehicle_util.getMinPurchaseTimeAndLifespan` / `getAge`: the oldest part's `purchaseTime` vs that part's `metadata.maintenance.lifespan * 1000`, with lifespans cached per model. A lifespan of 0 never counts as old.
     - Arg `"23/20"` (years, using `api.util.getDefaultYearDuration()`), metric = age % of lifespan.
     - Ages are read for 1/8 of the fleet per fleet pass (`entity % 8`), so each vehicle is re-checked about every 19 s. Earlier `fleet_old` alerts for vehicles outside the slice are carried over (`keepOld`).
   - **`fleet_idle_depot`:** `IN_DEPOT` vehicles (`getVehiclesWithState(IN_DEPOT)`) with `daysInDepot >= idleDepotDays`; context = depot name.
     - **`daysAtTerminal` (AT_TERMINAL) is skipped.** No base code reads it, and long terminal waits are usually deliberate (full load, timetable), so it would mostly be noise.
   - **State v3:** `memory = { stoppedSince, blockedSince, blockedBy }` (entity → integer maps, the same shape as the base `vehicle2problem`). v2 → v3 keeps alerts, counts and settings (new keys get defaults) and adds empty memory. v1 → v3 as before.
   - **Expected cost:**
     - *Vehicles group* (every 2.4 s at any speed):
       - one `getVehiclesWithState(EN_ROUTE)` list;
       - one `getSpeed` per en-route vehicle;
       - for standing vehicles only, a `PLAYER_OWNED` + `TRANSPORT_VEHICLE` copy;
       - for vehicles past their threshold only, `MOVE_PATH`/`MOVE_PATH_AIRCRAFT`, the line and names;
       - one `getBlockedTrains` call.

       `getVehiclesWithState` is not used by any base script. If it fails, we fall back to `forEachEntityWithComponent` + `tv.state` (one component copy per vehicle, the base pattern).
     - *Fleet group* (also every 2.4 s): the Phase 2 loop, plus one `TRANSPORT_VEHICLE` copy for 1/8 of the owned vehicles, plus one copy per vehicle in a depot.
     - *Allocations:* no per-vehicle tables except for standing / over-threshold / sliced vehicles.
     - *State writes:* `state:set` runs when timers change, i.e. at most once per vehicles slot. That is the same order as the base notifications state. (Phase 6 perf review: only timers ≥ 30 s old are saved, see Phase 6.)
     - *Target:* under 1 ms average per tick. Measure on a big save in phase 6.
4. **Line-quality metrics:** `line_overloaded`, `line_underused`, `line_bunching`. Thresholds tuned in game.
   **Status: implemented; offline tests pass; needs in-game verification and threshold tuning (TESTING.md §3, §10).**
   - **API evidence (units):**
     - *Target interval:* `api.engine.util.line.getMaxFrequency(line)` is 1/seconds. The base line window shows `math.floor(1 / maxFrequency)` as **Frequency** "Time interval between the vehicles" in `formatMinutesSeconds` (`line_util.tl:1350-1354`, `manager_window.tl:3972-3986`, `line_eow.script.tl:56-66`). We use `intervalMs = floor(1000 / f)`, assuming game seconds = `GAME_TIME.gameTime` / 1000 (the same clock as the base stuck rule's `1000 * 60 * 5`). `LineCargoInfo.frequency` (`type.d.tl:4185-4206`) is **not** used: no base code reads `getLineCargoInfo`, so its unit is undocumented.
     - *Utilisation:* `getLineCapacityUsages(line, false)` returns `{cargoTypeId + 1 : {used, capacity}}` (`util.d.tl:143-148, 195-198`); the base "Utilization" ("Percentage of the capacity that is currently used") is Σused / Σcapacity over cargo types (`cargo_util.tl:709-711, 895-907`, `statistics_react_util.tl:194-218`, `manager_window.tl:3957-3969`). `used` is cargo on board **now** (an instantaneous sample).
     - *Waiting:* `simEntityAtTerminalSystem.getLineStopSimEntitiesCount(line, stopIndex, cargoType)`, 0-based stop index (`system.d.tl:186-192`; the base passenger tooltip calls the sibling `getLineStopSimEntities(line, stopIndex, passengerCargoTypeId)` and indexes `stops[stopIndex + 1]`, `station_group.tl:648-680`). These are the people/cargo waiting **for this line** at that stop.
     - *Departures:* `TRANSPORT_VEHICLE.lineStopDepartures` "timestamps of the last departures at each line stop" (`engine.d.tl:1482-1483`). No base code reads it; we assume `gameTime` ms, one entry per stop (1-based). Wrong units fail quiet (every stop counts as stale or future, so no bunching rows); TESTING.md §10 checks them.
     - `calcLineStationThroughput` (the base **Rate**, "amount of cargo or passengers a line can transport per year", `manager_window.tl:3988-3999`) is not needed: capacity per trip and the interval give the same information per vehicle visit.
     - All four are called by the base **GUI** only. `getLineProblems`/`getLinesIssues` (same `api.engine.util.line`) run in the base sim script, so availability is likely; the quality scan runs in its own `pcall`, so a failure there keeps the Phase 2 line rows and the previous quality rows/timers.
   - **Timetables:** TF3 has none. `LoadState.WaitForScheduledDeparture` is shown by the base as "Ensuring safe distance" (`entity_window_util.tl:2283-2284`), i.e. the game's own spacing via the stop's "Max. Additional Wait ... to improve vehicle distribution" (`cargofilter_window.tl:826-829`). It is **not** a reason to skip a line. `autoDeparture` ("whether the vehicle departure is managed by the game or not") is read by nothing in base or official mods, so it is not used either (TESTING.md asks for its in-game values). Lines with a **full-load** stop (`stop.loadMode` 1 = FULL_LOAD_ANY, 2 = FULL_LOAD_ALL; the base departure toggle maps button index − 1 to `loadMode`, `cargofilter_window.tl:790-822`) are skipped for bunching: their departures follow demand by design.
   - **Metrics** (pure, `radar_checks.lineQuality` / `headways`; inputs from `radar.script.tl` `measureLine`). Eligible lines: owned, ≥ 2 stops, ≥ 1 vehicle, not `line_broken`.
     - `line_overloaded`: for every (stop, carried cargo type) with waiting ≥ `MIN_OVERLOAD_WAITING` (50), ratio = waiting ÷ per-trip capacity, where per-trip capacity = that cargo's `capacity` ÷ the line's vehicle count. Starts at ratio ≥ `lineOverloadFactor` (default **3**: it takes at least 3 vehicle visits to clear the stop). Row: worst stop, `arg = "<stop no.>|<waiting>|<stop name>"`, `metric = "2.8×"`.
     - `line_underused`: utilisation % = 100 × Σused / Σcapacity, lines with ≥ 2 running (EN_ROUTE / AT_TERMINAL) vehicles. Starts below `lineUnderusedPct` (default **10**). `metric = "8%"`, `arg` = vehicle count.
     - `line_bunching` (≥ 3 running vehicles, interval known, no full-load stop). For each stop, the running vehicles' last departure there, sorted, gives n − 1 headways plus the gap still open since the newest departure. A stop counts only if every vehicle has a departure there that is > 0, not in the future, and not older than 3 round trips (3 × n × interval). Over the valid stops we take the **median** stop's smallest headway (and its largest clump: consecutive headways below the clump threshold) and the **median** largest gap; medians keep one odd stop from flagging the line.
       - *Clump*: smallest headway < `lineClumpPct` % of the interval (default **20%**). `arg = "<in clump>|<vehicles>|<clump span s>|<target s>"`, `metric = "3/5"`.
       - *Gap*: largest gap ≥ `lineGapPct` % of the interval (default **300%**, i.e. 3×). `arg = "<gap s>|<target s>"`, `metric = "2.9×"`.
       - Needs in-game tuning: the base spacing ("Ensuring safe distance") may already dissolve clumps faster than the sustain time, and the interval may differ from Σheadways ÷ n on lines with long terminal waits.
     - **Sustain + hysteresis:** each condition must hold for `lineSustainMin` game-minutes (default **10**) before the row appears. Timers live in `memory.overloadSince / underusedSince / bunchingSince` (line → gameTime ms). Once running, a timer holds while the value is within `HOLD_FRACTION` (0.75) of its threshold (overload ≥ 0.75 × factor, underuse < pct ÷ 0.75, clump < clump ÷ 0.75, gap ≥ 0.75 × gap), so one sample just over the line doesn't restart it. Timers are dropped as soon as a measured line no longer meets the hold condition, or the line stops being eligible; each map is capped at `MAX_LINE_TIMERS` = 300 (oldest kept).
     - Detail text is made by the GUI model from the packed `arg` (split on `|`, the stop name last so it may contain `|`), with seconds formatted as `m:ss`.
   - **Settings** (`radar_settings.NUMBERS`, integers): `lineOverloadFactor` 3 (1-50, ×), `lineUnderusedPct` 10 (1-90, %), `lineClumpPct` 20 (1-90, %), `lineGapPct` 300 (120-2000, %), `lineSustainMin` 10 (1-240, min). Settable today via `ProblemRadar.setSetting`; the UI comes in phase 5.
   - **Rotating cursor:** each lines pass (every 2.4 s) measures eligible lines in `radar_checks.lineRotation(ids, lineCursor)` order: at most 8 lines, and no further line once 160 waiting-count queries have been made (always at least one). The cursor is the last line measured (Phase 5: a module-local variable in `radar.script.tl`, not saved; it restarts at the lowest id after a load). Lines not measured this pass keep their timers and their previous quality rows (with `firstSeen`), like `fleet_old`'s `keepOld`. A full rotation takes about L / 8 passes (200 lines: about 60 s), well inside the 10-minute sustain. No per-line static cache: `api.engine.getRevision(e).num[1]` is the entity's **creation** revision as the base uses it (`greenification_display.script.tl:80,124`), not a change counter, so it can't detect edited stops; and `LINE` is copied only for the ≤ 8 measured lines anyway.
   - **State v4:** `memory` adds `overloadSince`, `underusedSince`, `bunchingSince` and `lineCursor` (−1 = none; removed again in v5). v3 → v4 keeps alerts, counts, settings (new keys get defaults) and the vehicle timers, and adds empty line timers. v2 and v1 migrate as before. The vehicles scan now patches memory (`radar_checks.patchMemory`) instead of replacing it, so line timers survive vehicles passes.
   - **Expected cost per lines pass** (on top of Phase 2's line loop): for ≤ 8 lines, one `LINE` copy, one `getLineCapacityUsages`, one `getMaxFrequency`, one `getLineVehicles`, one `TRANSPORT_VEHICLE` copy per vehicle of those lines, and stops × carried cargo types `getLineStopSimEntitiesCount` calls (budget 160). Names only for stops with ≥ 50 waiting. (Phase 4 called `state:set` on every lines pass because the saved cursor moved; Phase 5 fixed that, see below.) Line-timer save size: ≤ 3 × 300 integers.
5. **Notifications + settings tab:** per-alert `off/passive/notify`, toasts only on newly appearing alerts.
   **Status: implemented; offline tests pass; needs in-game verification (TESTING.md §4-6, §8).**
   - **Notify level** `settings.notify[kind]` (`radar_settings.NOTIFY_KINDS` / `NOTIFY_DEFAULTS`, validated per kind; `setSetting { notify = { kind = level } }` merges a subset).
     - `off`: filtered before the merge (`radar_notify.filterOff`), so never listed or counted. Scan work is skipped where cheap: the station overflow loop / `getLineStationProblems`, the no-path failure lookups, the stuck scan (when `veh_stuck` and `train_blocked_by` are both off), the line-quality measuring (all three off), and each part of the fleet loop. Skipped scans drop their timers once, so turning a kind back on starts fresh. Exclusions still use the unfiltered alerts (e.g. trains in `veh_blocked` never become `veh_stuck` even with `veh_blocked` off).
     - Defaults: `notify` for `veh_stuck` and `line_no_vehicles`; `passive` for the rest. Base-reported kinds stay passive as decided. `veh_stuck` notifies because the base `stuck_vehicle` type is `initiallyIgnoredType = true` (no popup in a default game, HUD icon only) and uses one 5-minute rule without our station / harbour exclusions. `line_no_vehicles` (Critical, base "partly") toasts only after it has been listed for 2 game-minutes (`radar_notify.MIN_AGE_MS`), so lines being set up stay quiet. Note: several base problem types are `initiallyIgnoredType = true` (vehicle_warning, overcrowding, station_useless, vehiclecondition, cargo_rtc_warning): the base shows them as HUD/LVM icons but no popup by default; a player who wants toasts for them can set them to Notify.
   - **Decisions** (`radar_notify.step`, pure, once per full scan cycle after the fleet slot):
     - state `notified` (id → time) holds listed ids already notified; `notifyCleared` (id → time it cleared) holds recently cleared ones. A cleared id that returns within `COOLDOWN_MS` (10 game-minutes) is marked notified without a toast; expired cooldowns are dropped.
     - at most `MAX_TOASTS` = 3 toasts per cycle, ordered tier → firstSeen → id; the rest are marked notified and summed in one `{ more = n }` summary toast.
     - `notifyPaused`: new alerts are marked silently (no backlog on resume).
     - caps: `notified` 300 (= stored alerts, it only holds listed ids), `notifyCleared` 100 (newest kept).
     - `changed` only on a transition, so `state:set` isn't triggered by an unchanged cycle.
   - **Notification type** `square_problem_radar::/radar/notify/radar_notification.script` (+ `.res.lua`: `guiType = "Problem"`, label "Problem Radar", `initiallyIgnoredType = false`). Sent from the engine thread with `api.cmd.makeScriptingSendEventCmd("", "Notifications", "add", { type, params, autoDismissDuration = 60000 })`, the base pattern (`company_growth.script.tl:100-105`, handler `notifications.script.tl:710-718`). Params are plain data (`ProblemRadarNotificationParams`: kind, tier, etype, label, context, code, arg, metric, entity, `entityRev` = creation revision, pos). The GUI side builds the title (`<kind>: <entity>`), description (the row detail + context) and icon with `radar_hud_model.notificationText`, and the click mirrors a row click (position for path problems, else the entity; `selectEntity` only while the entity exists and its creation revision is unchanged, like `entity_util.entityChanged0`).
     - Icons are per kind (base icons used by the matching base types: `stuck_vehicle`, `line_minus_x`, `terminal_full`, `relation_<vehicle>_minus/_repair`, ...) with a per-tier fallback, rather than strictly per tier: the base icons are semantic, so a kind icon reads better.

## Smoothing (anti-flicker, 2026-10-05)

**Status: implemented; offline tests pass (`test_checks.lua` "smoothing:", `test_settings.lua` smoothSec, `test_notify.lua` "smoothing:"); needs in-game verification (TESTING.md §3 "Smoothing").**

Problem: a full scan cycle takes ~2.4 s, so kinds without their own hysteresis (e.g. `station_overcrowded`, whose `overflow` flag toggles) came and went several times within seconds. Fix: one generic layer for **every** kind, in `radar_checks.merge` (the function that merges a scan group's fresh alerts into the state). Kinds with their own sustain / hysteresis keep it unchanged (line-quality timers + `HOLD_FRACTION`, `fleet_worn` +10 points, `veh_stuck` / `train_blocked_by` minute thresholds); smoothing comes on top.

- **Setting** `smoothSec` (`radar_settings.NUMBERS`, unit `"s"`, game seconds = `GAME_TIME.gameTime` / 1000, default **30**, range 0-600; **0 = off**, the previous behaviour). Settings tab: right column, first group "General" ("Smoothing: problems must persist / linger (game seconds)").
- **Appear:** a newly detected id goes into `state.pending` (not listed, not counted, not notified) with `firstSeen` = first detection. It is listed once it is detected at a scan ≥ `smoothSec` after that. A miss records `missedAt` (first undetected scan); a detection clears it; the entry is dropped only when missed for longer than the window. So a flag that toggles every scan still matures; a single blip never shows.
- **Clear:** a listed id that is not detected stays listed with its last data and `missedAt` set; detected again it just continues (`firstSeen` unchanged); missed for longer than the window it is removed.
- **firstSeen = listed time.** A pending entry that matures is listed with `firstSeen = now`. So the row's age, the sort order and `radar_notify.MIN_AGE_MS` all count from when the row became visible, and a toast never comes before its row (`line_no_vehicles` toasts ~30 s + 2 min after the line first lacks vehicles). radar_notify only sees `state.alerts`, so lingering rows neither clear nor re-toast.
- **Carried rows** (`alert.carried`, transient, stripped by merge, never saved): rows a scan keeps without re-checking them, i.e. the line-quality `keep` (lines not measured this pass), Phase 7's `line_unprofitable` keep (lines whose money was not re-checked), `fleet_old` `keepOld` (vehicles outside this pass's age slice) and `carryOver` after a failed (sub-)scan. They are no news: they neither clear a miss nor start or mature a pending entry. The engine passes listed **and pending** rows into these keeps (`listedAndPending` in `radar.script.tl`), so a pending line-quality or `fleet_old` entry survives a rotation longer than the window and matures when re-measured. Failure isolation still works: carried rows stay as before; a lingering row still clears after the window; the drop after `FAIL_DROP_AFTER` failures is a merge with no alerts, so those rows go after one more window.
- **Priming:** while `primeAll` is set (mod just added to a save, or a pre-v5 state), each group's first scan calls merge with `instant = true`: everything already there is listed at once (and marked notified silently, as before). Kinds switched to **Off** go at once (no linger, pending dropped).
- **Over the stored cap** (300): rows counted but not stored have no data to linger with and look new when re-detected. For a kind with such rows (`kindCounts[k]` > stored rows of k) new ids are listed at once (no count flicker), and its unstored rows still clear without lingering. Best effort, only with > 300 problems.
- **Paused game:** game time stands still, so nothing matures or clears while paused (smoothing holds); with `smoothSec = 0` it behaves as before.
- **State (still v5, lazy):** `state.pending : {ProblemRadarAlert}` (optional; `nil` when empty, so older saves are already valid), capped at `radar_checks.MAX_PENDING_ALERTS` = 200 (oldest first detection kept; a newer one just starts its window later); `alert.missedAt` (optional) on listed and pending rows. `upgradeState` copies `pending` when it is a table and never marks its absence as a change; merge sanitises entries (non-table / non-string id / unknown or off kind dropped). Alerts listed in an older save stay listed (they are in `alerts`, never made pending). Settings saved without `smoothSec` normalise to 30 (saved once, the usual `radar_settings.same` path). `merge` reports `changed` for pending transitions too, so `state:set` runs on transitions only (an unchanged pending entry does not rewrite the state).
